# Can a file the agent writes be pulled out of the sandbox? No.

Answered 2026-08-27, from three live sessions — no new session needed.

## What was checked

`client.beta.files.list(scope_id=<session_id>)` against three sessions that had
each run `flatten` and `repair_and_report`, so each had certainly written
`/workspace/snapshot.json` and `/workspace/plan.json`:

| Session | Status when checked | Files listed |
| --- | --- | --- |
| `sesn_019U2ezB9o9SYizbnDydSUgD` | idle (alive) | `vehicles.json`, `orders.json` |
| `sesn_013cXZjgq5V3r5L8okTcAaoG` | idle (alive) | `vehicles.json`, `orders.json` |
| `sesn_01CxSMumR87eubhLYkEUfgiv` | idle (alive) | `vehicles.json`, `orders.json` |

Only the two payloads `web.py` mounted. No agent-written file in any of them, and
the sessions were **idle, not terminated** — so this is not an artefact of
checking after the container was reclaimed.

Downloading even the mounts fails:

```
400 invalid_request_error
File `file_011CeTG8FAES2RrccjQ18UuJ` is not downloadable.
Only files generated by a tool (for example, the code execution tool) can be downloaded.
```

## Why, and why there is no workaround

The container's filesystem and the session's file store are different things.
`files.list(scope_id=...)` returns what the CLIENT uploaded as a mount; a file the
agent writes with `bash` never enters it.

The obvious workaround — the agent uploading the file itself through the Files
API — is closed by the environment: egress is MCP-only, so the sandbox cannot
reach `api.anthropic.com`. That is the same restriction that keeps the app-MCP
bearer out of the sandbox's reach, and it is not worth relaxing for a report.

So the only things that leave the sandbox are the model's own token stream
(messages, tool calls, tool results) and the custom tool's round-trip. That is why
`xas_allocation/planner_channel.py` exists: a planner-facing report has to ride
out on a tool result, and `web.py` was discarding every tool result.

## Dead code this exposes

Both of these are written against the assumption that agent-written files come
back, and neither can fire today:

- `web.py` `/session/{session_id}/files` — returns `{"files": []}` for every
  session once `MOUNTED_INPUT_FILENAMES` is filtered out.
- `static/index.html` `showNewOutputs()` — polls that route for ~4s after every
  idle and never finds anything, so no output bubble is ever rendered. The
  chart-viewing path it feeds (`web._render_mode`, the image/markdown branches,
  `/files/{file_id}/content`) is unreachable for the same reason.

Not removed: it is pre-existing code outside the change that found it, and it
would start working unchanged if agent-written files ever became retrievable.
Do not build anything new on it without re-running the check above.
